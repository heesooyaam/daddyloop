# Задачи и пул воркеров

Начни с `/new` в CLI, кнопки **Новая сессия** на сайте или `/new` у бота. На сайте сначала опиши цель, затем выбери воркспейс; обычно его папку менять не нужно. В CLI и Telegram следуй шагам `/new`. Можно прислать GitHub issue, тикет Tracker или существующий PR в GitHub, GitLab или Arcadia.

```bash
daddy new --workspace App "https://github.com/acme/app/issues/42"
daddy sessions
daddy talk SESSION_ID "Возьми ещё https://github.com/acme/app/issues/43"
```

Сообщения в существующей сессии получает тот же daddy. Он читает требования, создаёт задачи, назначает воркеров и проверяет результат. Для независимого разговора используй `/new` или явно попроси создать новую сессию. В подключённой группе Telegram у неё появится отдельная тема.

Ответ координатора на открытый вопрос автора возвращает исправление тому же воркеру. Уточнение сохраняется в задаче и доступно при следующем независимом ревью.

Когда воркер оспаривает опубликованное замечание, задача показывает «Ждёт решения daddy». daddy сверяет аргументы воркера с требованиями. Если нужен выбор владельца, в карточке появляется конкретный вопрос и Telegram упоминает владельца. Если вопрос остаётся без ответа, бот напоминает о нём через 30 минут.

## Архитектура перед реализацией

Кнопка **Поставить в очередь** и команда Telegram `/task ОПИСАНИЕ` по умолчанию запускают отдельный ход планирования с доступом к коду для чтения. Можно передать URL issue, чтобы учесть описание и комментарии. Планировщик сверяет готовый план с репозиторием или пишет новый, формулирует критерии приёмки и передаёт сохранённый результат воркеру. Существенный открытый вопрос ждёт ответа. Реализация и независимое ревью получают один и тот же план.

Чтобы пропустить этап для одной задачи, сними флажок **Проверить архитектуру и план до реализации** или отправь `/task --no-plan -- ОПИСАНИЕ`. В разговоре с daddy сначала можно обсудить дизайн и шаги. В рабочей области GitHub daddy создаёт issue или добавляет согласованный план в существующий тикет до назначения работы. По умолчанию реализация использует его сразу. Для отдельной проверки попроси daddy проверить архитектуру и план перед реализацией.

Архитектор наследует движок, модель и уровень рассуждений общего ревьюера. Чтобы выбрать профиль для сессии, открой **Настройки сессии → Архитектор** и сними флажок **Как у общего ревьюера**. Для конкретной задачи выбери профиль в форме **Поставить в очередь → Выбрать модель → Архитектор** или в карточке задачи. Чтобы вернуть наследование, поставь флажок обратно. В Telegram настройки доступны через `/models → Архитектор` и кнопку **Архитектор** в карточке задачи. Например, `/task --architect-model МОДЕЛЬ --architect-effort high -- Почини поиск` задаёт профиль планирования для одной задачи. Разработчик использует профиль своего воркера. Настройка применяется к ожидающим и следующим ходам планирования. Начатый ход заканчивается на выбранной для него модели.

При одном движке архитектор и разработчик работают в общем диалоге конкретной задачи. Каждый ход получает свою модель и права. При разных движках разработчик получает сохранённый Markdown-план. Независимый ревьюер использует свой диалог сессии.

## Прямая постановка задачи

Нажми **В очередь** на панели задач или отправь `/task ОПИСАНИЕ` в Telegram. Задача появится с одним и тем же ID в обоих интерфейсах. Открой её на сайте или отправь `/task DADDY-ID`, чтобы увидеть этап, воркера и PR. Команда `/queue` показывает открытые задачи.

Воркер может создать тикеты или расследовать сбой и вернуть отчёт. daddy проверяет его перед завершением задачи. Проверенный отчёт доступен на сайте и через `/task DADDY-ID`. Сохранённые изменения кода проходят обычное ревью PR.

При постановке можно выбрать номер воркера, модель и уровень рассуждений. Без номера сервис выберет свободного воркера. Если указана модель, сервис сначала ищет свободного воркера с подходящим профилем. Если совпадений нет, этот профиль получит первый свободный воркер.

Открой **Воркеры** на сайте или отправь `/workers` в Telegram, чтобы увидеть номера воркеров, их модели и задачи. В настройках конкретного воркера можно сменить модель для следующей задачи. Параметр **Применить к текущей задаче** перезапускает активный шаг в той же рабочей копии. В Telegram для этого есть `/worker НОМЕР МОДЕЛЬ УРОВЕНЬ` с параметром `--force`. [Команды Telegram](../telegram/ru.md#задачи-и-воркеры)

Если задача застыла после слияния PR, открой её карточку на сайте или через `/task DADDY-ID` в Telegram и выбери **Проверить слияние**. Сервис сверит коммит с платформой и поставит отдельное ревью фактического результата. Подтверждение результата и обязательные проверки завершают задачу и освобождают место в пуле.

## Размер пула

```bash
daddy pool SESSION_ID 3
```

По умолчанию один воркер, максимум — восемь. Команда запрашивает целевой размер, планировщик применяет его асинхронно. При уменьшении `3 → 1` занятые воркеры заканчивают **всю задачу**, включая ревью, исправления и CI; только затем лишние места освобождаются. В задаче с автослиянием GitHub место остаётся за воркером до подтверждения слияния. После ревью задача ожидает слияния, а конфликт возвращается тому же воркеру с его рабочей копией и историей. Пауза и ожидание твоего ответа сохраняют место за задачей. Новый запрос размера заменяет предыдущий.

Лимиты памяти и процессов хоста могут разрешать меньше одновременных ходов, чем мест в пуле. Зависимости задают порядок, но не объединяют ветки. daddy сам решает, где полезен параллелизм: увеличение лимита не заставляет запускать лишних воркеров.

## Ревью и управление

Сервис открывает GitHub PR и GitLab MR сразу готовыми к ревью. Сервис автоматически публикует завершённые ревью. В GitHub он также публикует сохранённые замечания незавершённого ревью, сверив коммит, владельца и тексты. Воркер может исправлять их, пока остаётся открытым вопрос по требованиям. Сохранённые исправления отправляются в тот же PR или MR. Воркер получает опубликованный снимок замечаний. Незавершённая проверка, спор или устаревшая ревизия оставляют задачу открытой. Для завершения задачи с PR нужны обязательные проверки CI и подтверждение плана, если оно требуется. Автослияние для GitHub по умолчанию выключено.

Для существующей GitHub issue укажи её URL как источник задачи. Сервис распознаёт ссылку отдельным сообщением и явную строку вида «Тикет GitHub — https://github.com/owner/repo/issues/42» для выбранного репозитория. Остальные ссылки в описании служат контекстом. В PR импортированной задачи сервис добавляет связь для закрытия issue при слиянии в основную ветку.

Указания отправляй в основной чат daddy. Отчёты задач показывают ход работы и предлагают подтвердить план, если это требуется. При подтверждении сервис повторно проверяет ревизию и поколение задачи.

`/pause` приостанавливает сессию, `/resume` продолжает её. Закрытие CLI или браузера отключает только клиент. Остановка сервиса — другое действие: прерванная работа сохраняется и требует продолжения после проверки. Подробнее — [эксплуатация](../operations/ru.md).

## Автослияние в GitHub

В вебе или Telegram открой настройки сессии и включи **Автослияние PR в GitHub**. Настройка распространяется на уже проверенные открытые PR и будущие задачи сессии. В карточке задачи выбери **Как в сессии**, **Включено** или **Выключено**. Явный выбор для задачи имеет приоритет.

Если GitHub подтверждает конфликт с целевой веткой, daddy ставит исправление в очередь воркеров. В рабочей копии сервис объединяет точные версии веток, воркер разрешает конфликт и проверяет результат. Сервис отправляет коммит обычным push в тот же PR. Затем daddy заново проверяет изменения и ждёт зелёного CI. Если воркеру нужно решение о поведении кода, вопрос появляется в карточке задачи.

Для открытого PR сервис читает текущий коммит целевой ветки непосредственно из GitHub. Если целевая ветка продвинулась во время исправления конфликта, обычный push сохраняет результат в ветке PR, а daddy проверяет его с учётом новой базы. В списке задач веба и в /queue в Telegram видна причина ожидания автослияния, в том числе для черновика PR.

При исчерпании лимита GitHub сервис сохраняет срок ожидания для хоста. Он возобновляет опрос и проверяет фактическое состояние PR после сброса лимита. Сохранённое исправление отправляется обычным push после сверки веток. Если целевая ветка продвинулась, GitHub должен подтвердить её историю. Независимое ревью проверяет новую ревизию. Для ревью после таймаута доступна одна автоматическая повторная попытка.

Сервис ждёт завершения независимого ревью, публикации результата с закрытыми замечаниями и зелёного CI на текущей ревизии. GitHub сверяет переданный SHA и применяет правила репозитория. Из разрешённых способов сервис предпочитает squash, затем merge-коммит, затем rebase. Результат или причина ожидания видны в карточке задачи.
