# Reviewloop

Локальный сервис, который связывает постоянные сессии автора и независимого ревьюера вокруг GitHub PR и GitLab MR.

Обсуди замечание с тем, кто его нашёл, опубликуй итоговое ревью — автор получает опубликованные комментарии, исправляет код и возвращает новую ревизию на проверку. Markdown-план проходит тот же цикл в отдельном PR. Разрешение начать реализацию задаётся отдельно от публикации замечаний.

## Запуск

Нужны Git и Node.js 24 LTS. Для настоящих агентских сессий нужен авторизованный Codex CLI, проверено с `0.153.4`. Демонстрация работает без GitHub, GitLab и вызовов моделей.

```bash
./scripts/bootstrap.sh
./scripts/reviewctl.mjs serve --demo
```

`bootstrap.sh` при необходимости устанавливает Node **внутрь `.tools/node`**, проверяет SHA-256 официального архива, ставит зависимости и собирает проект. Системный Node не заменяется. Если Node 24 уже доступен: `npm ci && npm run build`.

Открой **http://127.0.0.1:4317**. Токен входа находится в `.reviewloop/access-token`, вывести его можно командой:

```bash
./scripts/reviewctl.mjs token
```

Нажми **Try a demo loop**. Будет создана явно помеченная демонстрационная задача: замечание → обсуждение → публикация → исправление → повторное ревью. Демонстрационный агент и PR имитируются; реальные изменения в сторонних репозиториях не выполняются.

Для dev-хоста из исходной задачи запуск настроен с более строгим контролем диска:

```bash
./scripts/reviewctl.mjs serve --demo --min-disk-gib 100 --max-disk-percent 80
```

При доступе с другой машины используй SSH-туннель:

```bash
ssh -L 4317:127.0.0.1:4317 your-dev-host
```

## Подключить настоящий PR или MR

1. Авторизуй Codex обычным способом (`codex login`), если он ещё не авторизован.
2. Добавь личные токены платформ, затем запусти `reviewctl doctor`.
3. Подключи PR через **Attach a PR** или CLI.

Поддерживаются переменные `GITHUB_TOKEN` / `GH_TOKEN`, `GITLAB_TOKEN` / `GLAB_TOKEN` и файлы `~/.tokens/github`, `~/.tokens/gitlab`. Токены читаются backend и не записываются в репозиторий, API-ответы или аргументы команд. Черновики создаются от имени владельца токена.

GitHub: права чтения содержимого, чтения checks/statuses и записи pull requests; для автоматического push также нужна запись содержимого. Fine-grained PAT должен предоставлять доступ к нужным репозиториям. GitLab: пользовательский токен с `api` и доступом к проекту. Права на push и защищённые ветки всё равно проверяет сервер.

Для self-hosted установки:

```bash
export REVIEWLOOP_GITLAB_HOST=gitlab.example.com
export REVIEWLOOP_GITLAB_TOKEN_FILE=/secure/path/gitlab-token
```

Аналогично поддерживаются `REVIEWLOOP_GITHUB_HOST` и `REVIEWLOOP_GITHUB_TOKEN_FILE`. Дополнительно можно хранить токены в `~/.tokens/gitlab-<host>` / `~/.tokens/github-<host>`. Общий токен не отправляется произвольному хосту из PR-ссылки.

```bash
./scripts/reviewctl.mjs doctor
./scripts/reviewctl.mjs attach https://github.com/owner/repo/pull/42 \
  --repo /absolute/path/to/repo \
  --requirements /absolute/path/to/requirements.md
```

Автор начинает новую сессию при первом исправлении. `--author-thread <id>` позволяет продолжить существующий Codex thread: сначала прекрати параллельное управление им из другого клиента. Все следующие запуски продолжат этот же thread, а ревьюер сохранит отдельный.

После присоединения сервис создаёт собственные рабочие копии в `.reviewloop/workspaces/<task-id>/`. Исходная рабочая копия пользователя не переключается и не сбрасывается. Авторские правки коммитит сервис; обычный push не перезаписывает конкурирующие коммиты. `--no-auto-push` оставляет коммиты локально.

**Публикация — ручная по умолчанию.** Можно нажать Publish в Reviewloop или в родном интерфейсе PR. `--auto-publish` либо настройки задачи разрешают автоматическую публикацию завершённых ревью. Автоматический merge не реализован.

### План и реализация

Создай отдельный PR с Markdown-планом и подключи его с `--kind plan`. После завершения ревью и CI нажми **Approve plan**. Затем подключи PR реализации с `--plan <task-id>`. В задачу копируются **конкретная принятая ревизия и полный текст изменённых Markdown-файлов**, а не ссылка на изменяющуюся ветку.

Для PR без CI задача остановится на **Waiting for checks**. Вкладка Context позволяет записать обоснованное исключение для этой ревизии; либо заранее отключи обязательный CI в настройках задачи.

## Интерфейс и команды

Веб-панель показывает задачи, роли, черновики, опубликованные замечания, решения, исходные требования и журнал событий. Кнопка **Discuss with reviewer** прикрепляет конкретный комментарий к сообщению. Вкладки Reviewer и Author обращаются к разным постоянным сессиям. В Activity раскрываются подтверждённые результаты вызовов инструментов и ошибки. Уведомления браузера включаются кнопкой с колокольчиком.

```bash
reviewctl list
reviewctl show <task-id>
reviewctl chat <task-id> --role reviewer 'Объясни сценарий из первого комментария'
reviewctl publish <task-id>
reviewctl pause <task-id>
reviewctl resume <task-id>
reviewctl retry <task-id>
reviewctl reconcile <task-id>
reviewctl logs <task-id> --follow
reviewctl approve-plan <task-id>
reviewctl waive-checks <task-id> --reason 'Проверки выполнены вручную на этой ревизии'
```

В примерах `reviewctl` — это `./scripts/reviewctl.mjs`; опционально зарегистрируй bin через `npm link`. Глобальные `--data-dir` и `--url` позволяют управлять другой установкой. После зависшего/прерванного ревью `retry` продолжает проверку текущего черновика; после ошибки автора `resume` продолжает исправления, сохраняя его рабочую копию.

## Как устроена надёжность

- SQLite WAL хранит задачи, очередь, поколения запусков, сессии, точные снимки опубликованного Markdown, решения и журнал внешних операций.
- Каждый результат связан с head/base/start SHA и версией контекста. Поздний ответ старого поколения не переводит новую ревизию дальше.
- Ревьюер сам вызывает инструменты добавления, редактирования и удаления native-комментариев. Backend не пересказывает их в собственные формулировки.
- Автор получает фактически опубликованный набор после пользовательских правок. Неопубликованные комментарии и приватная переписка с ревьюером не включаются в его контекст.
- Намерение внешней записи фиксируется до запроса. После потери ответа сначала выполняется сверка; при неопределённости слепой повтор запрещён.
- Автор может принять или оспорить замечание; подтвердить исправление должен ревьюер. Ранее отклонённые и отложенные замечания сохраняются как решения.
- Лимиты раундов, повторения одинаковых замечаний, времени запуска и доступных ресурсов останавливают цикл с понятным состоянием ожидания.
- После перезапуска незавершённые задания требуют сверки и явного продолжения. Уже опубликованное ревью не порождает повторный запуск автора при каждом опросе.

## Разработка и проверки

```bash
npm run check                 # TypeScript, unit/contract/integration tests, production build
npx playwright install --with-deps chromium
npm run test:e2e              # Browser workflow and mobile layout
npx tsx scripts/smoke-codex.ts # Optional live Codex tool call + persistent thread resume
```

Последняя команда использует авторизованный Codex и делает два коротких модельных вызова. Она проверяет протокол, не публикует комментарии и не меняет рабочие файлы. Отчёт сохраняется в `.reviewloop/codex-smoke.json`.

Для разработки UI: `npm run dev` и в другом терминале `npm run ui`. API и производственная сборка работают одним Node-процессом; долгие запуски выполняются дочерними процессами Codex. По умолчанию активен только один агент.

Если bootstrap установил локальный Node, перед командами `npm` добавь его в PATH текущего терминала: `export PATH="$PWD/.tools/node/bin:$PATH"`. Обёртка `scripts/reviewctl.mjs` выбирает локальный Node самостоятельно.

## Репозитории GitHub и GitLab

```bash
./scripts/reviewctl.mjs create-remotes --name reviewloop --push
```

Команда создаёт **private** репозитории в личных пространствах владельцев токенов, добавляет HTTPS-remotes `github` и `gitlab` и по `--push` отправляет `main` с тем же токеном. Без авторизации соответствующий шаг помечается отложенным. Существующий remote с другим адресом сохраняется; в уже существующий публичный репозиторий эта команда код не отправляет.

На текущем хосте локальных токенов GitHub/GitLab пока нет. Доступный коннектор GitHub подтверждает аккаунт, но не предоставляет создание репозиториев и не передаёт свои credentials локальному приложению. Поэтому публикация проекта и живой прогон native-черновиков пока отложены.

## Лицензия

Выбор лицензии оставлен владельцу проекта перед публичной публикацией. Сейчас репозиторий предназначен для локальной разработки; команда создания remotes использует private-видимость.
